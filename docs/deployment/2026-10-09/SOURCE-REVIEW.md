## 优先修复

### P1：Sonnet 5.5 的上下文窗口估算回退值错误

`src/anthropic/converter.rs:305` 的 `get_context_window_size` 中，1M 列表包含 Sonnet 5，却漏掉 Sonnet 5.5，使其回退到 200K。`src/anthropic/stream.rs:1644` 和非流式 `src/anthropic/handlers.rs:1509` 使用该函数把上游上下文百分比换成 token。

现场只读检查：`/v1/models` 中 `claude-sonnet-5.5` 的窗口是 1,000,000，当前无对应 customModels 覆盖。因此，缺少 provider 精确 tokenUsage、走上下文百分比回退时，该阶段 token 总量按应有值的 1/5 计算；后续输出扣除及缓存分摊仍会进一步改变最终字段，不能简单把所有历史账单直接乘五。

建议统一模型元数据来源，优先用上游模型窗口，并补齐回退表。验证连字符/点号别名、流式/非流式、provider 精确用量优先级，避免修复窗口后覆盖精确用量。

### P1：客户端 Key 使用非密码学随机数生成

`src/admin/client_keys.rs:564` 的 `generate_client_key` 使用 `fastrand::usize`，创建和轮换入口均调用它。fastrand 不适合生成认证秘密；字符串长度不能弥补随机源选择的问题。

建议用操作系统密码学随机源生成至少 32 字节随机值，编码为 hex/base64url，并正确处理熵源失败。此结论不等于已证实当前密钥泄露；当前生产入口 Key 是部署时由 Python secrets 生成并继承的，不是该函数生成。

### P1：上游失败仍可能产生模拟缓存命中

`src/anthropic/handlers.rs:939` 在真正调用上游前执行 `compute_cache_usage`。`src/anthropic/cache_metering.rs:974` / `:979` 已写本地/远程缓存，查询时还续期。若首次请求超时、被拒绝或失败，后续同前缀请求可能得到“缓存读”；并发请求也可能命中尚未完成请求写入的条目。

建议拆为查询、暂存写入计划、成功提交三步；失败不写入也不续期，明确流中断提交策略。用失败后重试和两个并发首次请求验证。不应以此模拟状态对外宣称真实上游缓存。

### P2：客户端额度上限不是严格预算约束

`src/admin/client_keys.rs:466` 只检查已结算的 total_credits，`:524` 在请求结束后才累计费用。多个并发请求可在余额尚未更新时全部放行；即使单请求，也可能在结束时跨过上限。现有锁保证数据访问互斥，不等于预留在途费用。

建议明确界面提示为软上限，增加每 Key 在途请求限制、原子预算预留与完成/取消结算。Kiro 成本若无法提前获得严格上界，就不能承诺绝对不超支；应使用保守预算和阈值并披露误差。验证并发、断流、重试与缺少 metering 的场景。
