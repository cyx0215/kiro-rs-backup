## 源码定位及边界

- `src/anthropic/cache_metering.rs:892` 起：累计哈希要求前缀内容一致，从每个断点回溯最多 20 个位置，并只保存实际断点。因此历史块变化或旧断点不在查找范围内，都可能使长前缀失配。还没有实时结构证据确定是哪一种。
- `src/anthropic/cache_metering.rs:93` 起：先按估算比例划分缓存覆盖，再按命中比例拆为读/写。长前缀失配后，覆盖范围内的大部分 token 会归入写入。
- `src/anthropic/stream.rs:1483` 起：优先上游精确 usage，否则使用上下文百分比/本地估算及模拟缓存分摊。当前样本不能证明总 token 精确正确。
- 早期缓存快照的长前缀估算约 168 万 token，而输出账单约 63 万 token。估算被用于比例分摊，并非直接原样上报；这个差值本身不能证明总 token 被放大。
- 现有日志未提取到数值 contextUsageEvent，trace 也没有保存断点位置、最深命中位置或历史块变化位置。因此不能把上下文窗口倍率错误或历史变化视为已证实根因。

下一步应在测试版增加不含正文、密钥和实际会话 ID 的结构诊断：块数量、断点位置、最深命中位置、过期/回溯范围和首次前缀变化位置，以及总 token 来源。用自然新增调用验证后，再决定是否修正匹配或计量；不直接提高缓存命中率或调低价格来掩盖差异。
